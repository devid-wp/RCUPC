# RCUPC — Security Model

Даже если RCUPC задуман для LAN, он даёт полный контроль над ПК. Поэтому архитектура с
Phase 1 оставляет «крючки» под безопасность, а реализация сосредоточена на Phase 11.
Этот документ — модель угроз и дизайн, **не** готовая security-система.

---

## 1. Модель угроз (LAN)

| Угроза | Реалистичность | Последствие |
|---|---|---|
| Постороннее устройство в той же сети подключается случайно | высокая | неавторизованный доступ/ввод |
| Пассивный прослушивающий (Wi-Fi, ARP-spoof) | высокая в общих сетях | утечка экрана и ввода |
| Активный MITM | средняя/высокая в общих сетях | перехват и подмена |
| Replay старого handshake | средняя | обход аутентификации |
| Случайное подключение к «своему» хосту с чужого клиента | средняя | нежелательный контроль |
| Компрометация клиента | средняя | ключи/host становятся доступны |
| Атака на открытый порт (fuzzing) | средняя | краши/утечки |

Базовое допущение: LAN **не** доверенная. Домашняя сеть — условно доверенная, но протокол
не должен на это полагаться.

---

## 2. Цели безопасности

1. **Authentication** — обе стороны уверены, кто напротив.
2. **Encryption** — трафик (особенно видео) не читается пассивно.
3. **Authorization** — host решает, разрешён ли ввод, а не только «подключение».
4. **Защита от случайного подключения** — без явного согласия host никто не управляет ПК.
5. **Replay resistance** — nonce/challenge в handshake.
6. **Forward secrecy** — по возможности (TLS 1.3/Noise дают её).

---

## 3. Pairing (сопряжение)

**Цель:** установить доверие между конкретным host и конкретным client один раз, без общего
доверенного сервера (его нет).

Варианты:

| Вариант | Как работает | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **Одноразовый код + PAKE** (SPAKE2) | host показывает код, client вводит; обе стороны выводят общий секрет | устойчив к MITM при коротком коде, не требует PKI | реализация PAKE сложнее | Phase 11, предпочтительно |
| **Код → сертификат** | код подтверждает обмен публичными ключами, дальше pinned cert | проще в реализации, понятно | нужен аккуратный out-of-band код | Phase 11, практичный вариант |
| **QR / файл с fingerprint** | fingerprint ключа сверяется глазами | прозрачно | требует UI | позже |

**Результат pairing:** обе стороны хранят:
- идентификатор/`device_id` партнёра;
- публичный ключ/fingerprint;
- список выданных разрешений и срок жизни.

Хранение:
- Windows host: DPAPI (шифрование под пользователем) + файл в `%APPDATA%`.
- Linux client: ключ в `~/.config/rcupc` с правами `0600` и/или OS keyring (libsecret).

## 4. Authentication / Encryption

### 4.1. Рекомендуемый путь: переиспользовать TLS 1.3

- **TCP:** стандартный TLS 1.3, mutual auth через self-signed сертификаты, **pinned** после
  pairing. Host-сертификат можно сгенерировать при первом запуске.
- **QUIC:** TLS 1.3 встроен — идеальный вариант при переходе на QUIC (Phase 6+).
- **UDP data plane:** либо внутри QUIC (datagrams), либо отдельный **DTLS 1.3**, либо слой
  **Noise** (например, Noise XX/IK) поверх UDP.

Почему TLS как основа: зрелость, аудит, forward secrecy, готовые Go-реализации (`crypto/tls`,
`quic-go`), минимум собственной криптографии.

### 4.2. Handshake-сообщения (см. `PROTOCOL.md`)

`AUTH_BEGIN/CHALLENGE/RESPONSE/RESULT` — либо «обёртывают» TLS-установку, либо используются
для challenge-response поверх уже установленного TLS (вторая ступень, подтверждающая, что клиент
владеет ключом pairing'а). Nonce гарантирует свежесть.

### 4.3. Что НЕ делать

- Не изобретать собственный шифр/KDF.
- Не использовать «просто shared secret» без KDF и nonce.
- Не полагаться на «в LAN безопасно».

### 4.4. Крипто-агностичный протокол

`pkg/protocol` работает поверх уже защищённого канала и не знает деталей шифрования.
`pkg/transport` отвечает за то, чтобы канал можно было «завернуть» (TLS/QUIC/Noise) или
оставить открытым на ранних фазах. Это позволяет включить security одной опцией.

## 5. Authorization

- **Разрешения на сессию:** view-only / control (ввод) / audio. По умолчанию — минимально
  необходимые; «control» требует явного согласия.
- **Consent host:** при подключении host показывает запрос «Client X хочет управлять»; без
  явного подтверждения (если не настроено «доверенное устройство») ввод запрещён.
- **Индикация:** постоянный видимый индикатор (tray/title) «идёт удалённое управление» и
  горячая клавиша экстренного разрыва.
- **Fine-grained:** отключать ввод, но оставлять просмотр; ограничивать клавиши (например,
  не пробрасывать Ctrl+Alt+Del).

---

## 6. Защита от случайного подключения

- **Не слушать 0.0.0.0 без необходимости** — по умолчанию bind на конкретный интерфейс/host.
- **Pairing обязателен** для установления сессии (после Phase 11); до этого — dev-режим с
  явным предупреждением.
- **Allow-list** устройств и/или IP-подсети (опционально).
- **Idle timeout:** при простое контролируемая сессия завершается.
- **Auto-lock экрана → разрыв/пауза** управления (по желанию).
- **Лимит попыток** подключения и backoff, чтобы не превращать порт в оракул.
- **Порт нестандартный** — мера слабая, но снижает шум сканеров; не заменяет аутентификацию.

---

## 7. Размещение в roadmap

- **Phase 1:** `transport` умеет быть обёрнутым в TLS; handshake содержит зарезервированные
  AUTH-сообщения (пока no-op). Bind на конкретный интерфейс.
- **Phase 11:** pairing, mutual TLS (или QUIC+pin), consent UI, permissions, хранение ключей,
  replay-защита, индикация.
- **Ранее:** не реализуем, но не принимаем архитектурных решений, которые сделают Phase 11
  болезненной (например, не «зашиваем» отсутствие слоя поверх транспорта).

---

## 8. Что не делать сейчас

- Не внедрять полную крипто-систему.
- Не делать PKI/CA, LDAP, cloud-identity — вне целей.
- Не хранить пароли в открытом виде там, где можно хранить ключ/pinned fingerprint.
- Не блокировать развитие проекта требованием «сначала всё зашифровать»: интерфейсы готовим,
  реализацию — на Phase 11.
